# 《悬案》播放触发缓存设计

## 目标

当电视盒子选择《悬案》第 N 集时，继续立即播放现有第三方 HLS 源，同时让 `192.168.1.5` 在后台缓存第 N 集，并低优先级预取第 N+1 集。后续播放优先读取已验证完成的局域网 MP4。

## 范围和边界

- 仅限 `cache-service/catalog/xuanan.tsv` 中的 01–17 集；不接受任意 URL。
- 服务运行在 `onehao@192.168.1.5`，程序位于 `/home/onehao/iptv-cache-service`，媒体位于 `/vol2/iptv-cache`，使用 `systemd --user` 与端口 `8788`，不使用 Docker。
- 不增加管理页面。提供 APK 使用的触发接口和只读状态接口。
- 第一次播放不会等待下载完成，也不会中途切换正在播放的流。

## 架构和数据流

1. APK 选择《悬案》第 N 集时，异步调用缓存服务的受限触发接口；网络失败不影响现有播放。
2. 服务将 N 写入高优先级队列；若 N+1 仍在目录范围内且未就绪，则写入低优先级队列。
3. 单个 worker 依次执行 FFmpeg 直拷贝。每集依次使用主源、备用源，完成后使用 `ffprobe` 校验，再原子地从 `.part` 改名为 MP4。
4. 服务为已完成文件生成本地播放 URL；APK 在下次播放时将该 URL 放在现有主/备源之前。
5. 服务只公布 `ready` 文件。下载中的文件、失败文件和队列状态仅通过状态接口可见。

## 接口

- `POST /api/v1/xuanan/episodes/{episode}/trigger`：只接受两位编号 `01`–`17`；返回当前集与预取集状态。
- `GET /api/v1/xuanan/episodes/{episode}`：返回状态和仅在就绪时出现的本地 URL。
- `GET /healthz`：返回服务可用性。
- `GET /xuanan/episodeNN.mp4`：仅静态服务已完成媒体。

## 失败处理

- APK 的触发或状态请求超时、失败时，保留当前第三方主/备用源播放逻辑。
- 同一集的重复触发必须幂等，不创建重复下载。
- 主源失败后尝试备用源；两者失败则记录 `failed`，后续新的播放触发可重新排队。
- worker 只处理一个下载，避免占满目标主机的双核 CPU、USB 磁盘 I/O 与外网带宽。

## 验收

- 单元测试证明：触发当前集会排入高优先级，同时将下一集排入低优先级；重复触发不重复排队；已就绪集返回本地 URL。
- Android 单元测试证明：《悬案》本地 URL 就绪时排在原始来源前，不就绪时维持原有来源。
- 目标服务器上 `systemctl --user` 服务持续运行，`/healthz` 可访问，真实触发请求进入队列；在至少一集完成后，从局域网 HTTP 地址取得媒体并能被 APK 播放。
